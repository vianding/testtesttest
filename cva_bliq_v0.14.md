1. Preserve the core v0.13 recommendation

The recommended methodology remains the companion CVA paper’s M0 indexed-face-based liquidation-recovery approach, implemented using:

* One trader-facing economic recovery mark, (R_{\mathrm{eff}}).
* A centrally governed three-state liquidation-recovery distribution.
* Three state-specific deterministic-recovery CVA calculations, aggregated with governed weights, where the implementation assumptions are satisfied.
* Exceptional non-disposal or non-realization as a separate contractual stress rather than an automatically calibrated fourth state.

At the reference mark:

Liquidation outcome	Weight	Recovery on indexed face
Severe distressed sale	30%	20%
Distressed orderly sale	50%	40%
Resilient sale	20%	65%
Weighted mean	100%	39%

The proposed additive mapping is:

[
R_k(R_{\mathrm{eff}})

R_k^0+(R_{\mathrm{eff}}-39%),
]

where

[
R^0=(20%,40%,65%),\qquad
w=(30%,50%,20%).
]

This mapping is transparent, monotonic and convenient for a single trader mark. It preserves state spacing and leaves the centrally governed probabilities unchanged.

Do not introduce a second desk input, trader-controlled probabilities or unnecessary M0 subcategories.

Keep the distinction between:

* (R_{\mathrm{eff}}): the desk’s economic recovery mark, equal by construction to the mean of the governed distribution.
* (R_k): individual liquidation-recovery outcomes generated by central configuration.
* (R_{\mathrm{LE}}): an exposure-specific loss-equivalent deterministic recovery, derived from the resulting nonlinear loss and not a universal issuer mark.
* Portfolio-CVA-equivalent scalar: a separate numerical inversion of a complete CVA calculation, potentially dependent on portfolio composition and model conventions.

Do not substitute one for another.

The historical calibration remains evidence-informed rather than statistically identified. The seven sovereign episodes provide useful severity and dispersion evidence but cannot estimate uniquely defensible French conditional probabilities. The 30/50/20% weights remain documented expert judgment.

Do not recalibrate them simply to make a historical average match the model.

2. Priority technical review: inspect the actual XVA source code

This is the most important new task in v0.14.

The current infrastructure is understood to support one deterministic scalar recovery independent of simulated market paths. However, the scalar’s actual economic meaning and insertion point have not yet been verified.

Inspect the existing XVA implementation, relevant pricing code, configuration, interfaces and companion CVA methodology before deciding whether a code change is needed.

Do not rely solely on variable names or documentation. Trace the parameter through the relevant calculation.

2.1 Establish what the scalar recovery actually controls

Identify:

1. Where the recovery input is defined, configured, passed and consumed.
2. Whether it is a recovery on:
    * Sovereign collateral proceeds;
    * Collateral market value;
    * The defaulted bond claim;
    * The Dealer’s counterparty claim;
    * A generic LGD or default payoff;
    * Or another quantity.
3. The denominator against which recovery is applied.
4. Whether the scalar enters before or after:
    * Collateral liquidation;
    * Collateral credit;
    * Close-out;
    * The positive-part loss calculation;
    * Contractual waterfall allocation;
    * Any counterparty recovery or LGD.
5. Which event activates the recovery calculation.
6. Whether the code distinguishes the sovereign collateral credit event from the relevant Dealer/counterparty default event.
7. Whether the parameter is used consistently across default times and simulated market paths.
8. Whether the scalar also affects any other product or portfolio calculation, creating an unintended side effect if repurposed.

Required output: a compact trace of the recovery parameter from configuration to final CVA contribution.

For each material finding, cite the actual source file, function or class, and relevant code location. If the code is incomplete or ambiguous, explicitly record that limitation.

2.2 Verify the intended Bliq insertion point

The intended economic chain is:

[
\text{Sovereign event}
\longrightarrow
\text{Collateral claim/disposal}
\longrightarrow
B_\tau^{\mathrm{liq}}
\longrightarrow
B_\tau^{\mathrm{avail}}
\longrightarrow
L_\tau^{\mathrm{Dealer}}.
]

Bliq supplies a conditional liquidation-recovery assumption on indexed collateral face:

[
F_\tau=N_\tau^{\mathrm{pool}}IR_{\tau^-},
\qquad
B_\tau^{\mathrm{liq}}(k)=F_\tau R_k^{\mathrm{liq}}.
]

The Dealer loss is conceptually:

[
L_\tau^{\mathrm{Dealer}}(k)

\left[
V_\tau^{\mathrm{co}}(k)

B_\tau^{\mathrm{avail}}(k)
\right]^+,
]

with the appropriate close-out and collateral-credit conventions.

Determine whether the existing scalar can directly represent the intended (R_k^{\mathrm{liq}}).

If it already controls the correct liquidation proceeds before Dealer loss is calculated, recommend reusing the existing implementation.

If it controls a different quantity, identify the smallest targeted code change needed to make the recovery input control the intended collateral-liquidation proceeds.

Do not propose a full path-dependent recovery framework merely because the current scalar has the wrong insertion point.

The user has indicated that a targeted code change is acceptable if necessary.

2.3 Verify conditional-event consistency

The weights (w_k) describe alternative collateral liquidation outcomes conditional on the relevant sovereign event. They are not probabilities of the sovereign event occurring.

Check how the existing CVA engine handles:

* The event triggering collateral liquidation.
* The Dealer or counterparty default event.
* Event ordering and timing.
* Paths on which the sovereign collateral event does not occur.
* Paths on which the Dealer loss is not exposed to the sovereign collateral recovery assumption.
* Any interaction with credit-curve calibration or counterparty LGD.

The weighted-run expression

[
\mathrm{CVA}_{\mathrm{dist}}

\sum_{k=1}^{K}w_k\mathrm{CVA}(R_k)
]

must not be presented as universally exact without specifying the assumptions.

It is exact for the intended fixed-mixture construction when each deterministic run applies the same model conventions, the recovery states are properly conditioned on the relevant event, the weights are constant for the relevant modeled circumstances, and the weighted outputs are linear combinations of the intended scenario results.

If the existing engine applies the scalar to unrelated events or to paths where the modeled liquidation does not occur, determine whether the expression still implements the intended economics.

If not, propose a narrowly scoped correction.

Also distinguish two questions:

* Does a weighted set of deterministic runs exactly represent the chosen fixed-mixture model?
* Is that fixed-mixture model an adequate approximation to real-world dependence among sovereign distress, rates, inflation, market liquidity, exposure, collateral value and default timing?

The first is an implementation question. The second is a model limitation requiring sensitivity testing, not necessarily immediate engine redesign.

2.4 Verify repeated-run consistency

For the three state-specific runs, establish whether the following remain identical except for the intended recovery assumption:

* Market scenarios and random-number setup.
* Exposure and close-out conventions.
* Observation and default-time treatment.
* Netting and collateral conventions.
* Discounting and numeraires.
* Default probabilities.
* Any other recovery or haircut applied elsewhere.

Check whether the CVA outputs are genuinely additive under the chosen aggregation.

If the engine has material run-to-run Monte Carlo noise, recommend common random numbers or another practical comparison method, where supported.

2.5 Recommend the right next implementation step

After inspecting the code, choose one of the following conclusions:

Case A — Existing scalar is already economically correct

Retain the existing scalar-recovery interface and implement three deterministic CVA runs followed by weighted aggregation. No engine modification is necessary.

Case B — Scalar is applied to the wrong quantity, but the correction is local

Recommend the smallest code change that redirects or introduces the scalar as a liquidation-recovery input on the intended collateral resources, before Dealer positive-part loss.

Preserve the existing path-independent scalar design.

Case C — Existing engine structure cannot implement the intended recovery with a local change

Explain precisely why, using source-code evidence. Identify the minimum viable alternative and what would require a larger redesign.

Do not assume Case C without demonstrating the obstruction.

The paper should state the code-grounded conclusion, rather than continuing to say only that the scalar semantics are unverified if the source code permits verification.

Keep detailed implementation traces and proposed edits in the separate verification note or a compact appendix entry.

3. Priority accounting review: reconcile collateral credit and waterfall

Review v0.13 Section 5.2, particularly Equations (10)–(12), against the companion CVA methodology and available transaction evidence.

The purpose is to ensure that posted collateral and subsequent waterfall receipts are neither double counted nor omitted.

3.1 Establish the definitions

Confirm precisely what each variable represents:

* (V_\tau^{\mathrm{co}}): gross or net close-out, and what collateral credit it already incorporates.
* (C_\tau^{\mathrm{post}}): posted collateral amount or value recognized in close-out.
* (E_\tau^{\mathrm{rem}}): remaining positive claim after the relevant collateral credit.
* (B_\tau^{\mathrm{wf}}(k)): incremental waterfall resources, and whether posted collateral is excluded.
* (Rec_\tau^{\mathrm{Dealer}}(k)): incremental amount allocated to the Dealer.
* (B_\tau^{\mathrm{avail}}(k)): total resource credited against Dealer loss.
* (K_\tau^{\mathrm{sen}}): any separately evidenced senior costs or deductions.

Reconcile the definitions with the companion paper’s equations and actual code conventions.

3.2 Test the accounting numerically

Construct a small reconciliation with at least these cases:

1. No posted collateral: all recoverable resources arise through the applicable waterfall.
2. Partial posted collateral: part of the Dealer claim is already covered; incremental waterfall receipts cover only the remaining claim.
3. Posted collateral exceeds positive close-out: ensure no negative residual loss or double recovery.
4. Different timing or valuation bases: posted collateral is recognized at one time, while disposal receipts are realized later.

For each case, show:

* Gross close-out.
* Posted collateral credit.
* Remaining claim.
* Incremental waterfall receipts.
* Total credited resource.
* Final Dealer loss.

The reconciliation should show when the compact whole-pool approximation is valid and when it is not.

3.3 Decide what belongs in the main text

Retain in the main paper the essential conclusion:

Posted collateral and incremental waterfall proceeds must be combined consistently, without double counting, before calculating the Dealer’s residual positive-part loss.

Keep the minimum formula needed to explain the CVA interface.

If Equations (10)–(12) are too implementation-specific for the main narrative, move their detailed derivation and numerical reconciliation to Appendix E.

Do not discard the accounting analysis; it is essential support for the recommendation.
